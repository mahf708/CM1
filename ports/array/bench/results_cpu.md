# cm1x CPU performance sweep

Case: supercell_kessler (WENO5, TKE, open radiative BCs, Kessler), nx/ny/nz overridden; float64. Command: `python ports/array/bench/sweep.py --backends numpy,jax,torch --modes eager,jit --grids 20,40,40x40x80,80 --steps 5 --threads 0,1 --skip jax:eager:80x80x80,jax:eager:40x40x80 --timeout 1800`

- CPU: Intel(R) Xeon(R) Processor @ 2.10GHz (4 logical CPUs)
- Python 3.13.16, numpy 2.5.3, jax 0.11.2, jaxlib 0.11.2, torch 2.14.1+cu130, dask 2026.8.0, array_api_strict 2.6.1
- default torch threads: 4; numpy runs single-threaded elementwise; jax (XLA CPU) uses its own thread pool. `threads` = 1 pins torch (set_num_threads) / XLA (intra-op) to one thread for a like-for-like comparison with numpy.

## Notes (hand-written; not regenerated by sweep.py)

- jax jit is single-threaded in practice (the XLA intra-op flag makes no
  difference), so the jit-vs-numpy comparison is like for like. jax `init`
  (~13 s) is the eager jax model set-up (base state, init3d), not compile.
- torch eager with its default 4 threads vs 1 thread: 1.6-3.3x faster with 4
  threads on >= 40^3, the same as numpy with 1 thread.
- torch jit (`Model(..., backend="torch", jit=True)`): `torch.compile`
  (inductor, `dynamic=False`, `fullgraph=True`, C++ vectorization off) of the
  hot routines one by one (`Backend.kernel`: advs/advu/advv/advw, the
  acoustic small step, turbs/turbu/turbv/turbw, kessler; ~15 compiled
  variants), the rest of the step eager. With 4 threads it is 1.8x torch
  eager at 40^3 (0.20 vs 0.36 s/step), 2.0x at 80^3 and faster than jax.jit
  there (0.89 vs 1.00 s/step); jax.jit stays ahead on <= 40x40x80 (0.14 vs
  0.20 s at 40^3), where the eager remainder of the torch step (solve2
  glue, sound set-up, sfc_and_turb, BCs; ~0.1 s at 40^3) dominates.
  Compile: ~150-215 s per grid with a cold inductor cache (each run here
  starts with an empty `TORCHINDUCTOR_CACHE_DIR`); ~30 s with a warm cache
  (inductor's FX graph cache, by default under /tmp/torchinductor_$USER).
  Results equal torch eager to the last bit in these runs (no fast-math,
  no FMA contraction); tests/test_jit.py checks <= 1e-10 relative.
- torch.compile of the whole step (`jit_options={"whole_step": True}`) did
  not finish compiling within 25 min even at 20^3 (~25k ops, graph break at
  the data-dependent fallout trip count), so it is not in the sweep.
- Eager change in this sweep: saturation adjustment (kessler.satadj) stops its
  masked sweeps once no point is active (`Backend.fori_loop(..., until=)`;
  same bits; eager only): mp_driver 54 -> 20 ms per step on torch eager at
  40^3.
- dask.array runs and matches numpy (rel. diff 1.5e-17 at 12x12x16, 2 steps),
  but at ~150 s/step on that tiny grid (task-graph overhead of tens of
  thousands of small slice ops on single-chunk arrays); not in the sweep.
- array-api-strict: bitwise equal to numpy once implicit trailing ellipses in
  partial indexing (`a[k]` on a 3-D array, ~60 call sites) are allowed;
  otherwise the code is array-API conformant. Not a performance backend.
